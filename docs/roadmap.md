# 后续工作

当前版本已包含训练与评测代码、锁定推理权重的输入契约，以及命令行和 Web 演示。后续主要处理误报、连续视频评估和设备部署中的问题。

## 误报与时间聚合

UR Fall 在线测试中，30 次跌倒没有漏报，但 40 个正常活动中有 19 个误报。正常坐卧、跪地、弯腰和支撑动作仍容易与跌倒混淆。视频分数使用采样时刻最大值，长视频也更容易受到偶发高分影响。

下一步先固定检测器和模型权重，比较窗口分数到事件的时间聚合方式，记录事件召回、每小时误报、报警延迟和重复报警。再按动作、遮挡、人数和视频时长分析错误，区分视觉确认、轨迹输入与报警策略的影响。模型或策略更新后只在验证集重新选阈值。

## 训练稳定性与跨域差异

现有模型在不同数据域和随机种子下存在差异。需要补充重复训练、分域结果与区间估计，并在相同数据协议下比较几何、全局和 ROI 分支的作用。

数据划分、主人物人工修订、困难样本和缓存契约需要与训练配置一起保存。完整训练仍依赖原始数据、冻结特征缓存和审核 overlay；仅有推理权重不足以重建这些输入。

## 连续视频与多人场景

短片段测试还不能回答长时间运行中的误报频率。后续需要有授权的连续视频与事件起止标注，覆盖不同视角、光照、人数和遮挡，同时检查轨迹切换、人物丢失及历史状态的影响。

应用侧还需检查断流恢复、并发任务、资源释放和长时内存占用。默认推理最多确认 2 人，人数增加后的速度与稳定性应重新测量。

## 模型导出与设备运行

当前已验证 PyTorch 在线流程，尚未完成 ONNX、TensorRT、目标 NPU 或 INT8 的部署验证。

导出时需要固定 YOLO 的检测与 P3/P4/P5 特征契约，定义确认器的历史特征和有效掩码输入，并处理主机侧的采样、跟踪与状态维护。转换后应先比较逐人物分数和报警时刻，再检查 FP16/INT8 的精度变化。

性能测量需要说明设备、输入分辨率、人数、精度和预热设置，并分别记录算法耗时与包含解码的完整链路耗时。已有 CUDA 测量不能替代目标 NPU 上的延迟、内存和稳定性结果。

## 发布与使用

源码采用 AGPL-3.0，权重和第三方视频的发布范围仍需分别核实。后续发布会继续保留环境版本、模型哈希、测试配置和失败案例，方便复现与比较。当前状态见[发布说明](release.md)和[第三方材料说明](third_party.md)。
